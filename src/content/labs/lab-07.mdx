Words used in every part:

- **Hardware** — the physical parts of the phone: the camera, the vibration motor, the screen.
- **Permission** — the user’s answer (yes or no) to “may this app use the camera?”. Phones ask once per app.
- **Haptics** — short vibrations that tell the user something happened, like a tap on the finger.
- **Test** — code that runs a part of your app and checks the result. It says **PASS** or **FAIL**.
- **Build** — turning your project into an app file a phone can install (an **APK** on Android).
- **Native code** — the Kotlin (Android) or Swift (iPhone) code inside the phone app. Your code is **JavaScript**; packages like `expo-camera` bring the native code that talks to the camera.

### D · Haptics: feedback you feel

`expo-haptics` plays short vibrations. There are three kinds of call:

<Cards cols={3} items={[
  { tag: 'an outcome', title: 'notificationAsync(type)', text: '`Success`, `Warning` or `Error`: three different patterns. Smart QR uses Success and Error.' },
  { tag: 'a choice', title: 'selectionAsync()', text: 'The lightest tap: a choice changed. Smart QR uses it for **Flip camera**.' },
  { tag: 'a touch', title: 'impactAsync(style)', text: 'Like two objects touching: `Light`, `Medium`, `Heavy`, `Rigid` or `Soft`.' },
]} />

Two rules from Expo’s documentation shape Smart QR:

- **iPhones play no haptics while the camera is active** (and none in Low Power Mode). So Smart QR vibrates on the **result card**, after the camera closed.
- On Android, the vibration permission is added for you. Phones without a vibration motor throw an error, so every call is inside `try / catch`.

#### ② How it works

Three ideas explain the whole step:

- **A hook** is a function whose name starts with `use`. React lets you call it only at the top of a component. `useCameraPermissions()` comes from `expo-camera` and tells your component what the user answered.
- **React runs your component again.** A component is a function that React runs to draw the screen. When a hook or a state gets a new value, React runs the whole function again, from the first line.
- **The first `return` decides the screen.** `return` ends a function. The first `return` that runs gives the screen; the lines under it do not run.

#### ② How it works

- **`expo-haptics`** plays the phone’s own vibration patterns (Part 3 showed all of them). Smart QR uses two: **Success** and **Error**.
- **`async` / `await`.** Asking the phone to vibrate takes a moment. `notificationAsync` gives back a **Promise** — a value that is ready a little later. `await` waits for it, and `await` can only be used inside an `async` function.
- **`try` / `catch`.** Some phones and tablets have no vibration motor; there the call throws an error. `try { … } catch { … }` catches the error, so the app keeps working.
- **When.** iPhones switch haptics off while the camera is on. So Smart QR vibrates when the **result card** appears — after the camera has closed.

#### ② How it works

A phone has two cameras: the **back** camera (for QR codes, documents, photos) and the **front** camera (for the user’s face). `CameraView` shows one of them, chosen by its prop `facing`: `'back'` or `'front'`.

- **`facing` is a state** — a value the screen remembers (Lab 02: `useState`). Changing it with `setFacing` makes React run `ScannerScreen` again, and `CameraView` gets the new side.
- **The button does two things, in order:** a small tap you can feel, then the switch.
- **The switch uses a function.** `setFacing` can take the new value, or a function that gets the current value and returns the new one. The function form is safer: React always passes the newest value.

<Part n="5" title="Testing: three tools, three layers" time="12 min" />

A **test** is code that runs part of your app and checks the result with an **assertion** (“I expect this to equal that”). When you change the app later, the tests run again in seconds and tell you if something that worked is now broken — a **regression**.

Tests come in layers. The lower the layer, the smaller the piece it runs, and the faster it is:

<Part n="8" title="Deployment: EAS Build, Submit, Update" time="12 min" />

Expo Go runs your project only while your PC serves it. To give the app to others you need a **build**: the app file itself. **EAS** (Expo Application Services) does the work on Expo’s servers.

Words for this part:

- **Binary** — the installed app file: an **APK** (Android, installs with a tap), an **AAB** (Android App Bundle, the format Google Play wants) or an **IPA** (iPhone).
- **Signing** — a digital signature that proves who made the app. Android uses a **keystore** (a file with your key). Every update must be signed with the same key.
- **Profile** — a named set of build settings in `eas.json`: development, preview, production.
- **Internal distribution** — sharing a build with a link instead of a store.
- **Update** — new JavaScript sent to apps already installed (“over the air”), without a new binary.

### EAS Update: new JavaScript, no new build

Most changes are only JavaScript: a text, a style, a bug in `parseScan`. **EAS Update** sends them to every installed build without a new binary and without a store review:

<Terminal title="Terminal — once per project, then one command per update" lines={[
  '$ npx expo install expo-updates',
  '$ eas update:configure',
  '# make a new build once (the build must contain expo-updates), then for each change:',
  '$ eas update --channel preview --message "Show the Wi-Fi name" --environment preview',
]} />

<Explain parts={[['eas update', 'upload the JavaScript and images of the project'], ['--channel preview', 'to the builds made with the preview profile'], ['--message "…"', 'a note for you: what changed'], ['--environment preview', 'which EAS environment variables to use (needed since SDK 55)']]} />

The rule: an update reaches only builds with the same **runtime version** — the same native code. A new native package, a new permission text, a new icon: these change the binary, so they need a **new build**.
