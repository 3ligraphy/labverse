<Part n="1" title="REST APIs — HTTP verbs & query params" time="45 min" />

A **REST API** is a set of URLs ("resources") you talk to with plain HTTP. The verb says *what kind of thing* you're doing to that resource; the URL says *which* resource.

<Cards cols={3} items={[
  { tag: 'read', icon: 'search', title: 'GET', text: 'Read a resource. Never changes anything on the server — safe to call as often as you like.' },
  { tag: 'create', icon: 'sparkle', title: 'POST', text: 'Create a new resource, or run an action that is not a simple update (like "check in").' },
  { tag: 'replace', icon: 'file', title: 'PUT', text: 'Replace a resource with a full, new version. Send every field, even the ones that did not change.' },
  { tag: 'update', icon: 'wrench', title: 'PATCH', text: 'Update part of a resource — just the fields that changed. (Not used much in this lab, but you should recognise it.)' },
  { tag: 'remove', icon: 'close', title: 'DELETE', text: 'Remove a resource.' },
]} />

### Query parameters

A query string is the part of a URL after `?` — `key=value` pairs, joined with `&`. It never changes *which* resource you're asking for, only *how much of it*, or *which part*.

<Explain parts={[['GET', 'read, never changes anything'], ['/todos', 'the resource'], ['?done=true', 'a filter'], ['&limit=5', 'a page size']]} />

Common uses: **filtering** (`?done=true`), **search** (`?q=shoes`), and **pagination** (`?page=2&limit=20`). The server reads them off `request.url` — nothing about the verb or the body changes.

### fetch vs Axios

`fetch` is built into JavaScript — no install, but you handle JSON parsing and error status yourself. **Axios** is a small library (`npm install axios`) that does both automatically and reads a little shorter. They do the exact same job; this lab lets you pick either one.

<Cards cols={2} items={[
  { icon: 'cmd', title: 'fetch', points: ['+ Built in — nothing to install', '+ One fewer dependency to update', '- You call `JSON.stringify()` and `res.json()` yourself', '- `fetch` does not reject on a 404/500 — you must check `res.ok`'] },
  { icon: 'download', title: 'Axios', points: ['+ `res.data` is already parsed JSON', '+ Rejects automatically on a bad status — one `catch` handles it', '+ `axios.create({ baseURL })` avoids repeating the full URL', '- One more package in `node_modules`'] },
]} />

<Part n="2" title="GraphQL vs REST" time="20 min" />

**GraphQL** is a different way to ask a server for data: one URL (usually `/graphql`), and the client says exactly which fields it wants in a **query** (read) or a **mutation** (write).

<Cards cols={2} items={[
  { tone: 'good', icon: 'link', title: 'REST', points: ['+ Simple: a URL + a verb, works with plain fetch()', '+ Easy to cache (the URL is the cache key)', '- Over/under-fetching: you get whatever shape the endpoint returns'] },
  { tone: 'good', icon: 'sparkle', title: 'GraphQL', points: ['+ Ask for exactly the fields you need, nothing more', '+ One request can gather data that would be several REST calls', '- More setup: a schema, resolvers, a GraphQL client'] },
]} />

Rule of thumb: a small app with a handful of simple resources (this lab's attendance app included) → **REST**. A large app with many related, nested resources and picky mobile data usage → **GraphQL** starts paying for itself.

<Part n="3" title="Synchronous vs asynchronous code" time="30 min" />

**Synchronous** code runs one line at a time; each line waits for the one before it to finish. **Asynchronous** code lets a slow operation (a network call, a file read, a timer) run in the background while the rest of your program keeps going.

<Cards cols={2} items={[
  { icon: 'clock', title: 'Use sync for', text: 'Fast, in-memory work: math, string formatting, array transforms — anything that finishes in microseconds.' },
  { icon: 'cloud', title: 'Use async for', text: 'Anything that waits on something outside the CPU: `fetch()`, reading a file, a timer, a database query.' },
]} />

On a phone, the UI thread is the same thread your JavaScript runs on. A synchronous call that takes 3 seconds freezes the whole screen for 3 seconds — no scrolling, no taps. An async call frees the thread while it waits, so the UI stays alive.

<Part n="4" title="Authentication — Clerk vs BetterAuth" time="35 min" />

Both are ways to add sign-up, sign-in and sessions to an app without writing that logic yourself.

<Cards cols={2} items={[
  { icon: 'cloud', title: 'Clerk', text: 'A fully hosted auth service. You install their SDK and drop in prebuilt UI; Clerk runs the servers, the database and the dashboard.' },
  { icon: 'key', title: 'BetterAuth', text: 'An open-source auth library you self-host. You own the database and the server; BetterAuth gives you the logic, not the infrastructure.' },
]} />

```ts title="Clerk — initialize (Expo)"
// npm install @clerk/clerk-expo
import { ClerkProvider } from '@clerk/clerk-expo';

export default function RootLayout() {
  return (
    <ClerkProvider publishableKey={process.env.EXPO_PUBLIC_CLERK_KEY}>
      {/* your app */}
    </ClerkProvider>
  );
}
```

```ts title="BetterAuth — initialize (server)"
// npm install better-auth
import { betterAuth } from 'better-auth';

export const auth = betterAuth({
  database: { provider: 'postgres', url: process.env.DATABASE_URL },
  emailAndPassword: { enabled: true },
});
```

| | Clerk | BetterAuth |
| --- | --- | --- |
| Hosting | Clerk's servers | Your own server/database |
| Cost | Free tier, then per monthly active user | Free (you pay only for your own hosting) |
| Setup speed | Minutes — prebuilt UI components | Longer — you build the UI yourself |
| Control | Limited to what Clerk exposes | Full control over data and logic |
| Best for | Shipping fast, small teams, don't want to run servers | Full control, data residency rules, cost at large scale |

**Pick Clerk** when speed to launch matters more than owning the stack — most student projects and early-stage startups. **Pick BetterAuth** when you must self-host (cost at scale, data residency, or you already run your own backend).

### Objects: values with names

An **object** groups values under names. Each name is a **key**, and each key has a **value**. You read a value with a dot: `object.key`.

```tsx title="an object"
const student = { name: 'Mona Adel', year: 2, present: true };

student.name;     // 'Mona Adel'  ← the value stored under the key "name"
student.year;     // 2
student.present;  // true
student.age;      // undefined   ← this key does not exist
```

### Arrays: lists of values

An **array** is a list in square brackets. Each item has a position, called its **index**. Counting starts at 0.

```tsx title="an array"
const courses = ['Mobile', 'Web', 'AI'];

courses[0];      // 'Mobile'  ← index 0 is the first item
courses[2];      // 'AI'
courses.length;  // 3         ← how many items
```

An array can hold objects. This is the shape of almost every list an API sends: a class list, a list of products, a list of messages.

```tsx title="an array of objects"
const students = [
  { id: 1, name: 'Mona Adel', present: true },
  { id: 2, name: 'Omar Khaled', present: false },
];

students[1].name;  // 'Omar Khaled'
students.length;   // 2
```

### JSON: an object written as text

A server cannot send a JavaScript object over the internet. It sends **text**. **JSON** (JavaScript Object Notation) is the format of that text. It looks like an object, with stricter rules:

<Cards cols={3} items={[
  { icon: 'file', title: 'Keys in double quotes', text: '`{"name": "Mona"}`, never `{name: "Mona"}`.' },
  { icon: 'file', title: 'Strings in double quotes', text: '`"Mona"`, never `\'Mona\'`. Single quotes make the text invalid.' },
  { icon: 'close', title: 'No comments, no extra commas', text: 'JSON is only data: nothing after the last item, no `// notes`.' },
]} />

Two functions move between the two forms:

- `JSON.stringify(object)` turns an object into JSON **text**. Your app uses it to **send** data.
- `JSON.parse(text)` turns JSON text into an **object**. Your app uses it to **read** data it received.

<JsonTranslator />

```tsx title="the two directions"
const student = { name: 'Mona Adel', present: true };

const text = JSON.stringify(student);  // '{"name":"Mona Adel","present":true}'  ← a string
text.name;                             // undefined: a string has no keys

const again = JSON.parse(text);        // an object again
again.name;                            // 'Mona Adel'
```

### What an API is

Your app does not keep the class list itself. The list lives on a **server**: a computer on the internet that keeps data and runs code. Your app asks the server for data, or sends data to it.

An **API** (Application Programming Interface) is the list of addresses (URLs) a server offers, and the rules for each one: what to send, and what comes back.

### The parts of a request

A request has a **method**, a **URL**, and sometimes **headers** and a **body**.

<Explain parts={[['GET', 'the method: read data and change nothing'], ['https://labverse-indol.vercel.app', 'the server'], ['/api/lab5/students', 'the path: which data'], ['?present=true', 'the query string: a filter (Part 1)']]} />

- **Method**: what kind of action. `GET` reads, `POST` sends (Part 1 has all of them).
- **URL**: the full address: the server, then the path, then an optional query string.
- **Headers**: extra information about the request, for example "the body is JSON".
- **Body**: the data you send. A `GET` has no body. A `POST` usually has one.

### fetch: your first request in code

`fetch` is built into JavaScript. It sends a request and gives you the response. Read this code line by line:

```tsx title="a GET request with fetch"
async function loadAll() {
  const res = await fetch('https://labverse-indol.vercel.app/api/lab5/students'); // 1
  const data = await res.json();                                                // 2
  setStudents(data);                                                            // 3
}
```

1. `fetch(url)` sends a **GET** request to the URL. `await` waits until the response arrives. `res` is the response: `res.status` is the status code, `res.ok` is `true` for 200–299.
2. `res.json()` reads the body and turns the JSON text into an array. Reading takes time too, so it also needs `await`. (It does the `JSON.parse` step of Part 5 for you.)
3. `setStudents(data)` saves the array in state. React draws the screen again, now with the list.

To load the data once when the screen opens, call the function inside `useEffect` with an empty list `[]` (Lab 02):

```tsx title="load once, when the screen opens"
useEffect(() => {
  loadAll();
}, []);
```

<Part n="7" title="Waiting for the answer: await and errors" time="35 min" />

### async and await

A request takes time: often 0.1 to 2 seconds, sometimes more on slow Wi-Fi. `fetch` does not give you the response at once. It gives you a **promise**: a value that arrives later.

- `await` waits for a promise and gives you its value.
- You can write `await` only inside a function marked `async`.
- While one function waits, the rest of the app keeps working: buttons and scrolling still respond (you saw this in Part 3).

```tsx title="what await changes"
const res = fetch(url);         // no await: res is a promise, not the response yet
const res = await fetch(url);   // await: res is the response
```

### Two kinds of failure

A request can fail in two different ways, and your code must handle both:

<Cards cols={2} items={[
  { icon: 'wrench', title: 'The server answered with an error', points: ['A wrong URL (404), bad data (400), a server problem (500)', '`fetch` does **not** throw: check `res.ok` yourself'] },
  { icon: 'close', title: 'There was no answer at all', points: ['No internet, or a wrong server name', '`fetch` **throws** an error: catch it with `try` / `catch`'] },
]} />

```tsx title="safe request: both failures handled"
async function load() {
  try {
    const res = await fetch(url);
    if (!res.ok) {                  // the server answered with an error (404, 500, …)
      setMessage(`Error ${res.status}`);
      return;                       // stop: do not read the body
    }
    const data = await res.json();  // only for a good answer
    setMessage(`Hello, ${data.name}`);
  } catch {                         // no answer at all
    setMessage('No connection. Try again.');
  }
}
```

### GET reads, POST sends

To **send** data, the request needs three things that a GET does not have:

```tsx title="a POST request"
const res = await fetch('https://labverse-indol.vercel.app/api/lab5/echo', {
  method: 'POST',                                  // 1. send data
  headers: { 'Content-Type': 'application/json' }, // 2. the body is JSON
  body: JSON.stringify({ name: 'Mona' }),          // 3. the body, as JSON text
});
const data = await res.json();                     // the server's answer
```

1. `method: 'POST'`: this request sends data. Without it, `fetch` makes a GET, and a GET cannot carry a body.
2. `headers`: extra information. `'Content-Type': 'application/json'` tells the server how to read the body.
3. `body`: the data. It must be text, so `JSON.stringify` turns the object into JSON text.

```ts title="features/attendance/api.ts — fetch version"
import { getDeviceId } from '@/shared/device';

const BASE = 'https://<your-course-site-domain>/api/attendance';

export async function checkIn(name: string, studentId: string) {
  const res = await fetch(BASE, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ name, studentId, deviceId: getDeviceId() }),
  });
  const data = await res.json();
  if (res.status === 201) return { ok: true as const, entry: data.entry };
  if (res.status === 200 && data.already) return { ok: true as const, entry: data.entry, already: true as const };
  if (res.status === 409) return { ok: false as const, reason: data.error as 'device' | 'id' };
  if (res.status === 503) return { ok: false as const, reason: 'closed' as const };
  return { ok: false as const, reason: 'error' as const };
}
```

```ts title="features/attendance/api.ts — Axios version"
import axios from 'axios';
import { getDeviceId } from '@/shared/device';

const api = axios.create({ baseURL: 'https://<your-course-site-domain>/api' });

export async function checkIn(name: string, studentId: string) {
  try {
    const res = await api.post('/attendance', { name, studentId, deviceId: getDeviceId() });
    return { ok: true as const, entry: res.data.entry };
  } catch (err: any) {
    const status = err.response?.status;
    if (status === 409) return { ok: false as const, reason: err.response.data.error as 'device' | 'id' };
    if (status === 503) return { ok: false as const, reason: 'closed' as const };
    return { ok: false as const, reason: 'error' as const };
  }
}
```

Note the shape of the difference: Axios never reaches the success path on a 409 or 503 — a non-2xx status throws, so that logic moves into `catch`.
